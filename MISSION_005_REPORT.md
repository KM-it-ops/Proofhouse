## Gemini adapter structure and how it parallels/diverges from the OpenAI and Anthropic adapters

`adapters/gemini.py` follows the exact structural pattern of `adapters/openai.py` and `adapters/anthropic.py`: a class exposing `adapter_id`/`adapter_version` class attributes, constructed identically (`DiagnosticFactory`, `source_document`), with `capability_manifest()`, `describe()`, `check_capabilities(validated_ir)` (the same required/optional capability-decision loop, deliberately re-duplicated per MISSION-003/004's established reasoning), and `lower(validated_ir, resolution)` following the same fail-fast-on-required-gap shape, `canonicalize`/`canonical_sha256` artifact primitives, and `PRG-CAPABILITY-0001`/`PRG-ADAPTER-0001` diagnostic codes (both already registered, no new diagnostic registry entries needed).

It diverges from both prior adapters in three places Gemini's actual, documented model genuinely requires:

1. **`gemini_schema_subset.py` enforces a materially different, more permissive rule set than `openai_schema_subset.py`/`anthropic_schema_subset.py`.** Confirmed across multiple independent sources (official `ai.google.dev` Structured Outputs guide's own worked example, Firebase AI Logic's structured-output guide, and independent technical write-ups), Gemini's `responseSchema`/function-parameter subset does **not** require `additionalProperties: false` and does **not** require every declared property to appear in `required` — fields are optional by default, the opposite convention from OpenAI's and Anthropic's strict mode. The checker therefore only enforces base-type validity and array `items` presence, and deliberately never flags a missing `required` entry or an omitted `additionalProperties: false` as a violation. A dedicated test (`test_missing_additional_properties_false_is_not_a_violation`, `test_property_missing_from_required_is_not_a_violation`) proves this divergence directly using the same schema shape MISSION-003's OpenAI checker treats as non-compliant.
2. **Built-in/grounding tools are tracked as a distinct capability and a distinct artifact field, reusing Anthropic's `tools.server_executed@1` id rather than minting a new one.** `tools.function_calling@1` (reused id, same caller-defined/caller-executed meaning as OpenAI/Anthropic) is `supported`. `tools.server_executed@1` is reused, deliberately, from `anthropic.py` — the general "provider-hosted tool with no caller-side handler" concept (Anthropic's `web_search`/`code_execution`/`tool_search`; Gemini's `google_search` grounding/`code_execution`/Maps grounding) genuinely generalizes across both providers, unlike the reasoning capabilities below. `lower()` always emits distinct `function_tools` and `built_in_tools` top-level keys, never a single flattened `tools` field.
3. **A new `reasoning.thinking_level@1` capability**, not a reuse of OpenAI's `reasoning.effort_control@1` or Anthropic's `reasoning.extended_thinking@1`. Gemini's model is a genuine hybrid: a categorical `thinking_level` enum (structurally closer to OpenAI's scalar effort dial than to Anthropic's numeric budget) combined with a *mandatory* opaque thought-signature continuation token returned on essentially every function-call response (structurally related to, but stricter than, Anthropic's signature-preservation requirement — Gemini 3 returns a signature on every function-call response, not only when thinking blocks are explicitly preserved across a tool-use turn). Neither prior capability id would have honestly represented this shape, so this adapter introduces its own, always emitting an explicit `thinking` object (never omitted).

The adapter registry (`adapters/__init__.py`) now returns `gemini` from `list_registered_adapter_ids()` alongside `fake`, `openai`, and `anthropic`; `RESERVED_LIVE_ADAPTER_IDS` is now the empty frozenset — all four adapters in OAR-001-02's planned initial set are implemented. `base.py`'s `AdapterNotFoundError` docstring (describing `gemini` as reserved-but-unimplemented) was corrected to reflect that all three live-provider ids are now implemented — documentation-only, no behavior change.

## Capability manifest content, documentation sources, and corroboration method

Direct `WebFetch` attempts against `ai.google.dev` guide pages were redirected by the environment's context-mode hook before reaching page content — the same limitation MISSION-003 hit with `platform.openai.com` and MISSION-004 hit with `platform.claude.com`. Following the same discipline, every claim below was corroborated via `WebSearch` across multiple independent, distinct sources (official `ai.google.dev` guide pages and Google's own developer blog announcements, cross-checked against independent third-party technical write-ups, SDK issue trackers describing the same documented behavior, and Google Cloud's parallel documentation of the same underlying model) before being encoded into the manifest. Nothing below was asserted from a single source.

| Capability | Resolution | Basis |
|---|---|---|
| `output.structured_json@1` | `supported` | Gemini `responseSchema` (OpenAPI 3.0 Schema Object subset) |
| `tools.function_calling@1` | `supported` | Gemini function calling (`functionDeclarations[].parameters`, same OpenAPI-subset schema format) |
| `tools.server_executed@1` | `unsupported` | Genuine IR-representational gap, not a misreading of Gemini's capability — see below (id reused from `anthropic.py`) |
| `reasoning.thinking_level@1` | `conditional` | Model-specific (Gemini 3+ thinking-capable models only), matching the matrix's "Thinking levels/signatures with model-specific continuation rules" |

Machine-readable `limits` for the two `supported` capabilities (both carry the identical schema-subset limits, mirroring the "shared subset across structured output and function calling" shape corroborated for Gemini, the same sharing pattern confirmed for OpenAI and Anthropic):
- `additional_properties_required_false: false` and `all_properties_must_be_required: false` — the genuine, confirmed divergence: Gemini's official Structured Outputs guide's own worked example lists a `required` array containing only some of an object's declared properties, cross-checked against Firebase AI Logic's structured-output guide ("fields are optional by default... you can set fields as required to force the model to provide a value") and an independent technical blog reaching the same conclusion.
- `supported_types`: `string, number, integer, boolean, array, object, null` — the base type set the checker enforces, consistent with `responseSchema` being documented as an OpenAPI 3.0 Schema Object subset (which itself restricts `type` to this set, with `null` expressed via a type array matching modern JSON Schema convention, per the official guide and independent write-ups).
- `nullable_expressed_as`: type array including `"null"` — corroborated the same way as the two prior adapters.
- `property_ordering_supported: true` — `propertyOrdering` is a Gemini-specific, non-OpenAPI-standard extension field confirmed across the official guide and multiple independent technical write-ups; this adapter's `lower()` derives it deterministically from each schema's `properties` key order (see below).
- `additional_properties_anyof_ref_defs_supported_since: "2025-11 structured-outputs update"` — corroborated via Google's own developer-blog announcement of the update, cross-checked against an independent SDK issue tracker (`googleapis/python-genai#1815`, reporting the same behavior change) and independent technical write-ups describing the same expanded keyword support (including recursive `$ref`/`$defs` schemas, a capability explicitly *not* supported prior to this update per the same sources).
- `unrecognized_keywords_are_ignored_not_rejected: true` — corroborated via an independent technical write-up describing this failure mode; **not** independently confirmed to checker-verification confidence from an official source, so `gemini_schema_subset.py` does not attempt to enumerate an ignored-keyword list, consistent with the "don't misrepresent silently-ignored as rejected" discipline MISSION-004 applied to Anthropic's unenforced keywords.

`tools.server_executed@1` limits carry a `note` rather than schema limits: Gemini's API genuinely supports built-in/grounding tools (`google_search` grounding, `code_execution`, Maps grounding — corroborated via the official Grounding-with-Google-Search and Code-Execution guides, cross-checked against the official "Combine built-in tools and function calling" guide and Google's own blog announcement of Gemini 3's tool-context-circulation model), but PromptRig's **frozen** IR v0.1 `tools` array schema has no field to select a specific Gemini built-in tool or supply its configuration. Reported `unsupported` for the same reason MISSION-004 reported Anthropic's server tools `unsupported` — to make the representational gap explicit, not to imply Gemini itself lacks the capability.

`reasoning.thinking_level@1` limits (`thinking_level_known_values: [minimal, low, medium, high]`, `replaces_legacy_numeric_thinking_budget`, `thought_signature_required_with_function_calling`, `thought_signature_is_opaque_encrypted_token`, `thought_signature_must_be_echoed_back_on_continuation`, `multi_step_function_calls_each_carry_own_signature`) were corroborated from the official Gemini Thinking and Thought Signatures guides, cross-checked against an independent Medium technical write-up on migrating to Gemini 3's stateful reasoning model, a Google Cloud Enterprise Agent Platform doc describing the same thought-signature behavior, and an independent SDK-track technical guide. **Caveat, stated honestly:** the exact `thinking_level` enum member set is confirmed to vary by model generation (Gemini 3 Pro documents `LOW`/`HIGH`; other Gemini 3.x models document `MINIMAL`/`LOW`/`MEDIUM`/`HIGH`) — the manifest records the union of confirmed values rather than asserting one fixed, universal enum, since no single source confirms one canonical set across all thinking-capable models.

**No conflict found** between `PROVIDER_SELECTION_MATRIX.md`'s Gemini claims ("Broad multimodal, tool, grounding, and code-execution surfaces"; "Structured output with a supported schema subset"; "Function calling plus built-in tools"; "Thinking levels/signatures with model-specific continuation rules") and current documentation — all four were confirmed accurate, so the frozen matrix was not modified.

**Scope boundary, stated honestly:** exactly like the OpenAI/Anthropic checkers, `gemini_schema_subset.py` encodes only the constraints it could confirm with confidence. It does not add explicit enforcement for the newly-supported `anyOf`/`$ref`/`$defs` keywords (their presence is simply never flagged, matching their confirmed support), and it does not attempt to detect or reject `$ref` cycles (same known limitation as the OpenAI/Anthropic checkers, which also assume a tree-shaped schema) — this is a materially lower-risk gap for Gemini than for the prior two adapters, since recursive `$ref`/`$defs` schemas are now a confirmed-supported feature rather than a confirmed-unsupported one this checker would need to reject.

## How the built-in-vs-function tool distinction is represented in the artifact

`lower()` never produces a single generic `tools` field. It always emits two explicit top-level keys:
- `function_tools`: a list of `{"name", "description", "parameters"}` objects (no `strict` flag — unlike OpenAI's/Anthropic's tool payloads, Gemini's function-calling model has no confirmed strict/non-strict mode distinction to represent), one per IR `tools[]` entry that passed the supported-subset check when `tools.function_calling@1` was requested. Each `parameters` object includes a deterministically-derived `propertyOrdering` array when the underlying schema is object-typed with declared properties.
- `built_in_tools`: always present, always `[]` in v0.1, because the frozen IR cannot describe a Gemini built-in/grounding tool at all. When `tools.server_executed@1` is requested as `optional`, the request is recorded in `capability_decisions` (resolution `unsupported`) and lowering proceeds with `built_in_tools: []`. When requested as `required`, `lower()` fails explicitly via `PRG-CAPABILITY-0001` before any artifact is produced — a genuine required-capability-gap test (`test_lower_required_built_in_tool_capability_fails_explicitly`), not a synthetic `nonexistent@1` stand-in.

`test_lower_function_and_built_in_tools_are_never_flattened_into_one_field` asserts `"tools" not in payload` and both `function_tools`/`built_in_tools` are present and independently populated.

## How thought-signature/continuation-token state is represented in the artifact

`lower()` always emits an explicit `thinking` object — never omitted, regardless of whether `reasoning.thinking_level@1` was requested:
- Not requested: `{"requested": false}` (still an explicit key — `test_lower_thinking_not_requested_is_explicitly_absent_not_omitted` asserts this).
- Requested (required or optional — `conditional` resolution never trips the required-gap failure path): `{"requested": true, "capability_resolution": "conditional", "thinking_level": null, "thinking_level_note": "...", "thought_signature": {"required_when_function_calling": true, "opaque": true, "must_be_echoed_back_on_continuation": true, "note": "..."}}`.

`thinking_level` is explicitly `null` with an explanatory note (same treatment as OpenAI's missing effort field and Anthropic's missing `budget_tokens`). The `thought_signature` sub-object is deliberately structured, never a placeholder string — it records the *shape* of the continuation requirement (mandatory when function calling, opaque, must be echoed back) even though the frozen IR cannot supply an actual signature value, because IR v0.1 represents a single compiled request, not a multi-turn conversation, and has no field to carry a prior turn's signature into this artifact even in principle. This is recorded as a distinct, structurally deeper limitation from the `thinking_level` configuration gap — see the dedicated finding below.

## ADR-006 third-confirmation check

**Finding: Gemini hits the same gap. This is the third independent confirmation.**

ADR-006 defines the gap precisely: "no field through which a caller can specify a per-request reasoning or thinking configuration (for example, a reasoning-effort level, a thinking-token budget, or any other provider-facing control over extended/adaptive reasoning behavior)." Gemini's `thinking_level` — a categorical enum (`minimal`/`low`/`medium`/`high`, varying by model) that the caller sets per request to control reasoning depth — is squarely within that definition: it is exactly the kind of "provider-facing control over extended/adaptive reasoning behavior" ADR-006 describes, structurally closer to OpenAI's `reasoning.effort_control@1` (a categorical dial) than to Anthropic's numeric `budget_tokens`, but unmistakably the same category of caller-configurable reasoning control. `lower()` cannot source a concrete `thinking_level` value from any field in `PROMPTRIG_IR_V0_1.schema.json` — the same representational gap MISSION-003 found for OpenAI's `reasoning.effort_control@1` and MISSION-004 found for Anthropic's `reasoning.extended_thinking@1`'s `budget_tokens`.

This mission does **not** modify ADR-006, its status, or the frozen IR schema in any way — per the mission's explicit authority boundary, that decision belongs to the architect and owner, not to this mission. This finding is reported here, in its own subsection, so the escalation decision (per ADR-006's own stated "two independent confirmations already sufficient, but here is the third" threshold) can be made explicitly and separately from this mission's implementation work.

**A related but analytically distinct second finding, reported honestly rather than folded into the above:** Gemini's mandatory thought-signature continuation-token requirement is *not* fully the same kind of gap as ADR-006 describes. ADR-006 is specifically about a missing *caller-specified configuration* field (an effort level, a budget). The thought signature is different in kind: it is opaque state *returned by the provider* that the caller must echo back on a subsequent turn to preserve reasoning continuity — not a value the caller chooses at all. The frozen IR v0.1 cannot represent this either, but for a structurally deeper reason: the IR has no multi-turn/conversation-continuation concept whatsoever (it compiles a single request, with no field anywhere for "the previous turn's opaque state"). This is a genuine, additional representational gap this mission surfaced, worth recording distinctly rather than conflating with ADR-006's reasoning-configuration framing — it points toward a different, likely larger future IR question (multi-turn/session state modeling) than ADR-006's proposed `reasoning` block would resolve on its own. Recorded as new technical debt below, not folded into the ADR-006 finding above, and not acted upon here (no IR change is authorized by this mission).

## The `output_contracts[0]` question — Gemini as a third data point

Investigated per Scope item 6. Gemini's `responseSchema` structured-output model, per every corroborated source in this mission's research (the official Structured Outputs guide, Firebase AI Logic's guide, and independent technical write-ups), is a **single schema per request** — the same one-schema-per-call shape confirmed for OpenAI's `response_format` (MISSION-003) and Anthropic's `output_config.format` (MISSION-004). No source found any indication that a single Gemini API call can carry multiple simultaneous structured-output schemas.

**Conclusion:** this is now the third independent data point confirming the same provider-independent constraint. With three-for-three across structurally distinct providers (a strict-mode-with-JSON-Schema-flavored subset, a strict-mode-with-a-slightly-broader-subset, and now a permissive-by-default-with-OpenAPI-3.0-flavored subset), `output_contracts[0]`-only lowering is not a coincidental shortcut that happened to work for three unrelated APIs — it reflects a genuine architectural fact about how every corroborated LLM provider's structured-output mechanism works today (one schema per request). This mission's recommendation, going a step further than MISSION-004's "worth escalating... after a third data point either way": the finding is now well-established enough that it should be treated as **confirmed adapter-contract behavior**, not open technical debt requiring future resolution. The remaining, genuinely open question is narrower and different in kind: *why* `output_contracts` is an IR **array** at all if every current adapter only ever consumes index `0` — that is a legitimate, still-open IR-design question (multi-contract output routing, or format negotiation across multiple candidate schemas), but it is a design question for a future IR version, not a defect in any of the three adapters built so far. Recorded as a refined technical-debt item below, replacing the "revisit after a third data point" framing MISSION-004 carried forward.

## Technical debt

New, from this mission:
- **Thought-signature/multi-turn continuation state cannot be represented in IR v0.1 at all** — a distinct, structurally deeper gap from the ADR-006 reasoning-configuration finding (see the dedicated subsection above). The frozen IR has no conversation/session/multi-turn concept whatsoever; resolving this would require a different kind of IR extension than ADR-006's proposed `reasoning` configuration block, likely a future IR version's session/turn-state model. Not proposed or authorized here — flagged for the architect's awareness alongside the ADR-006 finding.

## Recommendation for what comes after MISSION-005

The four-adapter initial set (fake → OpenAI → Anthropic → Gemini) is now complete per OAR-001-02's ratified order. Recommended next priorities, roughly in order of what unblocks the most future work:

1. **Bring the ADR-006 finding to the architect for an explicit escalation decision.** This mission supplies the third independent confirmation ADR-006 itself said would be sufficient evidence to act on (it treated two as already sufficient to record the finding; a third, from a structurally different provider's mechanism, is now in hand). This mission does not propose a schema shape or timeline — that decision belongs entirely to the architect/owner per this mission's explicit authority boundary — but recommends it be taken up before any fifth adapter or IR v0.2 planning begins, since it will likely shape both.
2. **Scope a follow-up IR-design discussion for multi-turn/session state**, informed by this mission's new (and distinct from ADR-006) thought-signature finding. This is a materially larger question than a single `reasoning` configuration block and may deserve its own ADR rather than being folded into ADR-006's scope.
3. **Live-execution permission boundary design** — all four adapters now produce complete, well-tested offline artifacts; the natural next question is what a live-execution interface looks like (credential handling, the permission boundary `PROVIDER_ADAPTER_CONTRACT.md` already flags as separate and future) now that the adapter contract has been proven across four structurally distinct providers.
4. **Evaluation/repair scoping** — explicitly out of scope for all four adapter missions to date; now that compiled artifacts exist for every planned provider, this becomes a well-founded next initiative rather than a speculative one.
