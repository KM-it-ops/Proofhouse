## Anthropic adapter structure and how it parallels/diverges from the OpenAI adapter

`adapters/anthropic.py` follows the exact structural pattern of `adapters/openai.py`: a class exposing `adapter_id`/`adapter_version` class attributes, constructed identically (`DiagnosticFactory`, `source_document`), with `capability_manifest()`, `describe()`, `check_capabilities(validated_ir)` (the same required/optional capability-decision loop, deliberately re-duplicated rather than shared — continuing MISSION-003's explicit reasoning: independent reviewability, no coupling between adapters' tested behavior), and `lower(validated_ir, resolution)` following the same fail-fast-on-required-gap shape, `canonicalize`/`canonical_sha256` artifact primitives, and `PRG-CAPABILITY-0001`/`PRG-ADAPTER-0001` diagnostic codes (both already registered and generic enough to reuse — no new diagnostic registry entries were needed).

It diverges from `openai.py` in three places specifically because Anthropic's actual, documented model requires it (not for convenience):

1. **Client vs. server tools are tracked as two distinct capabilities and two distinct artifact fields.** `tools.function_calling@1` (reused id, same meaning as OpenAI's: caller-defined, caller-executed custom tools) is `supported`. A new `tools.server_executed@1` capability is added and deliberately left **unsupported** — see the dedicated section below for why. `lower()` always emits both `client_tools` and `server_tools` as separate top-level keys (never a single flattened `tools` key), so the distinction survives into the artifact regardless of which capability was actually requested.
2. **A new `reasoning.extended_thinking@1` capability**, not a reuse of `reasoning.effort_control@1`. Extended thinking is structurally different from OpenAI's scalar reasoning-effort dial: it involves signature-verified thinking blocks that must be preserved and returned unmodified across tool-use turns, `redacted_thinking` blocks that must not be filtered out, a `budget_tokens` minimum, and documented incompatibility with temperature/top_k overrides and forced tool choice. Reusing `reasoning.effort_control@1` would have silently implied OpenAI-shaped semantics for a mechanism that is not a simple effort level; a distinctly named, distinctly documented capability keeps that state honest.
3. **A standalone `anthropic_schema_subset.py`**, not a reuse of `openai_schema_subset.py`, following the same intentional per-adapter-module duplication precedent MISSION-003 established for `check_capabilities()`. The two confirmed hard constraints (`additionalProperties: false`, all-properties-required) are the same for both providers, but Anthropic's documented behavior for schema keywords beyond those two differs from what MISSION-003 could confirm for OpenAI (see Capability manifest section) — a shared module would have either under- or over-stated one provider's guarantees.

The adapter registry (`adapters/__init__.py`) now returns `anthropic` from `list_registered_adapter_ids()` alongside `fake` and `openai` (in that order); `RESERVED_LIVE_ADAPTER_IDS` shrinks to `{"gemini"}` only. `base.py`'s `AdapterNotFoundError` docstring (stale since MISSION-002, describing all three live-provider ids as "simply not implemented") was corrected to reflect that openai and anthropic are now implemented — a documentation-only fix, no behavior change.

## Capability manifest content, documentation sources, and corroboration method

Direct fetches of `platform.claude.com` guide pages were not reliably retrievable as usable body text through the available tools (the same limitation MISSION-003 hit with `platform.openai.com` — one `WebFetch` attempt was intercepted/redirected by the environment's context-mode hook before reaching page content). Following the same discipline as MISSION-003, every claim below was corroborated via `WebSearch` across multiple independent, distinct sources (official Claude Platform Docs pages plus independent third-party technical write-ups, other vendors' documentation of the same Anthropic API behavior, and — for tool-use — Anthropic's own public `anthropic/skills` GitHub repository) before being encoded into the manifest. Nothing below was asserted from a single source.

| Capability | Resolution | Basis |
|---|---|---|
| `output.structured_json@1` | `supported` | Anthropic Structured Outputs (JSON Outputs mode, GA as of `output_config.format`) |
| `tools.function_calling@1` | `supported` | Anthropic strict tool use (`strict: true` on client tool definitions) |
| `tools.server_executed@1` | `unsupported` | Genuine IR-representational gap, not a misreading of Anthropic's capability — see below |
| `reasoning.extended_thinking@1` | `conditional` | Model-specific; not available on all Claude models, matching the matrix's "Adaptive/extended thinking with preservation rules" |

Machine-readable `limits` for the two `supported` capabilities (both carry the identical strict-subset limits, mirroring the "shared subset across structured output and tool use" shape confirmed for Anthropic, same as OpenAI's):
- `additional_properties_must_be_false: true` and `all_properties_must_be_required: true` — corroborated directly quoting Anthropic's strict-tool-use guidance ("you must set `additionalProperties` to false on every object in the schema and list every property in the `required` array"), cross-checked against Google Cloud's Gemini Enterprise partner-model docs, Vercel's AI Gateway docs for the Anthropic Messages API, and an independent technical blog, all describing the same constraint.
- `supported_types`: `string, number, integer, boolean, array, object, null` (the base type set the checker enforces; Anthropic's docs additionally mention `enum`, `const`, `anyOf`/`allOf`, `$ref`/`$defs`, and standard string formats as supported, but this checker — like OpenAI's — does not add explicit checks for those, so they are not claimed as independently verified by the checker itself).
- `documented_but_unenforced_keywords`: `minLength, maxLength, pattern, minItems, maxItems, minimum, maximum, multipleOf` — corroborated across multiple independent sources (a synthesis of the official strict-tool-use and JSON-schema-limitations guides, cross-checked against AG2's Anthropic integration docs, genkit.dev's Anthropic plugin docs, and an independent Anthropic tool-schema validator write-up) as **present-but-silently-unenforced by Anthropic's constrained decoding**, not rejected. This is a materially different behavior from a hard violation, so `anthropic_schema_subset.py` deliberately does not flag these keywords as violations (see its docstring) — doing so would misrepresent "silently ignored" as "rejected."
- `recursive_schemas_supported: false` — corroborated the same way; not enforced by the walker (same known limitation as the OpenAI checker, which also assumes a tree-shaped schema).

`tools.server_executed@1` limits carry a `note` rather than schema limits: Anthropic's API genuinely supports server-executed tools (`web_search`, `web_fetch`, `code_execution`, `tool_search` — corroborated via Claude Platform Docs' tool-use overview/tool-reference/server-tools pages, cross-checked against an independent 2026 technical blog series on Claude's client/server tool split), but PromptRig's **frozen** IR v0.1 `tools` array schema (`PROMPTRIG_IR_V0_1.schema.json`, `additionalProperties: false`, fixed required fields `id/description/input_schema/side_effecting/approval`) has no field to select a specific server tool or supply its configuration. This is reported as `unsupported` to make that representational gap explicit, not to imply Anthropic itself lacks the capability.

`reasoning.extended_thinking@1` limits (`budget_tokens_minimum: 1024`, `preservation_required_when_used_with_tools`, `signature_field_required`, `redacted_thinking_blocks_must_be_preserved`, `incompatible_with: [temperature_override, top_k_override, forced_tool_choice]`) were corroborated from Claude Platform Docs' Extended Thinking guide, cross-checked against independent write-ups (a Medium/Substack technical guide, GitHub issues from two unrelated projects — `opencode` and `langchain` — independently describing the same signature-preservation requirement in production, and AWS Bedrock's documentation of the same underlying Claude behavior).

**No conflict found** between `PROVIDER_SELECTION_MATRIX.md`'s Anthropic claims ("JSON outputs and strict tool use, with schema limits"; "Typed client tools plus server-executed tools"; "Adaptive/extended thinking with preservation rules") and current documentation — all three were confirmed accurate, so the frozen matrix was not modified.

**Scope boundary, stated honestly:** exactly like `openai_schema_subset.py`, this module encodes only the two hard constraints it could confirm with confidence, plus the base type list. It does not add enforcement for `enum`/`const`/`anyOf`/`allOf`/`$ref`/`$defs` support (mentioned in docs but not independently checker-verified here), and it explicitly does not treat `minLength`/`pattern`/etc. as violations, per the corroborated "accepted but unenforced" behavior above.

## How the client-tool vs. server-tool distinction is represented in the artifact

`lower()` never produces a single generic `tools` field. It always emits two explicit top-level keys:
- `client_tools`: a list of `{"name", "description", "input_schema", "strict": true}` objects, one per IR `tools[]` entry that passed the strict-subset check when `tools.function_calling@1` was requested. Every IR-representable tool is, by construction, a client-executed tool (the frozen IR schema has no other shape).
- `server_tools`: always present, always `[]` in v0.1, because the frozen IR cannot describe an Anthropic server tool at all. When `tools.server_executed@1` is requested as `optional`, the request is recorded in `capability_decisions` (resolution `unsupported`) and lowering proceeds with `server_tools: []` rather than silently fabricating a payload for a tool the IR cannot actually specify. When requested as `required`, `lower()` fails explicitly via `PRG-CAPABILITY-0001` before any artifact is produced — a genuine required-capability-gap test (`test_lower_required_server_tool_capability_fails_explicitly`), not a synthetic `nonexistent@1` stand-in.

`test_lower_client_and_server_tools_are_never_flattened_into_one_field` asserts `"tools" not in payload` and both `client_tools`/`server_tools` are present and independently populated.

## How thinking-block/reasoning-preservation state is represented in the artifact

`lower()` always emits an explicit `thinking` object — never omitted, regardless of whether `reasoning.extended_thinking@1` was requested:
- Not requested: `{"requested": false}` (still an explicit key, not an absent one — `test_lower_thinking_not_requested_is_explicitly_absent_not_omitted` asserts this).
- Requested (required or optional — `conditional` resolution never trips the required-gap failure path, since `conditional != unsupported`): `{"requested": true, "capability_resolution": "conditional", "budget_tokens": null, "budget_tokens_note": "...", "preservation": {"signature_required": true, "must_return_thinking_blocks_unmodified_when_used_with_tools": true, "redacted_thinking_blocks_must_be_preserved": true}}`.

`budget_tokens` is explicitly `null` with an explanatory note, not a fabricated number: the frozen IR v0.1 has no field to source a concrete `budget_tokens` value from (same category of gap MISSION-003 recorded for `reasoning.effort_control@1` — no IR field to source a reasoning-effort value from either). This mission encountered the identical gap for Anthropic's analogous capability and handled it the same way: record the state explicitly (never silently drop it), leave the concrete-value question as an open IR-schema question for a future ADR rather than inventing a value or omitting the field.

## The `output_contracts[0]` decision (Scope item 5) — resolved here as: **not resolved, and explicitly not needed**

Investigated per Scope item 5. Anthropic's JSON Outputs / strict tool use model, per every corroborated source in this mission's research, is a **single schema per request or per tool** — the same one-schema-per-call shape as OpenAI's `response_format`. No source found any indication that a single Anthropic API call can carry multiple simultaneous structured-output schemas. Because the shape is the same for both providers, `output_contracts[0]`-only lowering is not an OpenAI-specific shortcut that happens to leak into the Anthropic adapter — it reflects a genuine, corroborated, provider-independent one-schema-per-request constraint. Anthropic's model therefore does **not** make this limitation matter more than it already did for OpenAI, so this mission explicitly chose **not** to resolve it, and is not silently carrying it forward unexamined either: the investigation was performed, the reasoning is stated here, and the technical debt entry is retained (see below) rather than closed or expanded.

## Technical debt

New, from this mission:
- `anthropic_schema_subset.py` encodes only the two confirmed hard constraints plus the base type list — it does not add explicit checks for `enum`/`const`/`anyOf`/`allOf`/`$ref`/`$defs` (documented as supported, but not independently checker-verified), and it deliberately does not warn when documented-but-unenforced keywords (`minLength`, `pattern`, etc.) are present, even though a future diagnostic could usefully flag "this constraint will be silently ignored by Anthropic's strict mode" as a warning-severity diagnostic distinct from the current hard-failure-only model. Not implemented here to avoid introducing a new diagnostic severity/behavior beyond this mission's scope.
- `tools.server_executed@1` is permanently `unsupported` under the current frozen IR v0.1 schema — this is not a bug to fix in this adapter, but a real IR-schema expressiveness gap. Resolving it would require an IR schema change (out of scope; the schema is frozen under `compiler-contract-freeze-v0.5`) to add some way of specifying a provider-hosted tool by name/config. Recommend a future ADR if server-tool support becomes a real requirement.
- `reasoning.extended_thinking@1`'s `budget_tokens` is always `null` in the lowered artifact — the frozen IR v0.1 has no field to source a concrete value from. Same category of gap as MISSION-003's `reasoning.effort_control@1` finding; both point at the same open IR-schema question (no per-request reasoning/thinking configuration surface in the frozen v0.1 IR) rather than two unrelated problems.
- No capability-mismatch test yet exercises `reasoning.extended_thinking@1` failing as a *required* capability that resolves to a hard `unsupported` (only the `conditional`-required-does-not-fail path is tested, since `conditional` is this capability's only real resolution in the current manifest) — matches the equivalent gap MISSION-003 recorded for `reasoning.effort_control@1`.

Carried over from `MISSION_003_REPORT.md`, explicitly investigated and **not** resolved here (see the dedicated decision section above):
- `lower()`'s structured-output handling considers only `output_contracts[0]` — investigated for this mission per Scope item 5; concluded Anthropic's model does not make this matter more than it already did for OpenAI (both are one-schema-per-request), so it remains recorded technical debt, not fixed.
- `openai_schema_subset.py`'s scope boundary (untouched, not this mission's concern).
- `_CODE_TO_EXIT` static mapping, `iter_schema_errors` first-failure-only behavior, TypeScript generator `oneOf`/`allOf`/`anyOf`/`patternProperties` gap, `doctor()`'s limited checks — all carried over, informational only, none blocked this mission.
